# Security analysis: source findings, not a deployed penetration test

Reviewed `firestore.rules`, authentication and Registrar modules, seal/unlock helpers, user/reward services, Grand Archives, and representative control-panel renderers at the revision recorded in README. No live database mutations, credential access, forged certificates, or exploitation were performed. Whether these rules are deployed is unknown.

## Authentication versus authorization

Google sign-in through Firebase establishes a UID. The Firebase SDK sends bearer ID tokens to Firebase services; a custom application JWT or traditional cookie-session CSRF layer was not found. That does not establish that OAuth domains, quotas, account controls, or deployed rules are correct. Browser redirects/hiding never replace resource authorization. Firestore rules must enforce access even for calls made outside the UI.

Firestore allows overlapping matching grants with OR semantics. Deny statements cannot cancel another matching allow. Unknown paths are denied when no allow matches. There is no production `celestialHypersim` match in the inspected rules. Proposed sandbox paths will therefore require reviewed deployment before any live access; the scaffold intentionally makes no such requests.

## Explorer policy

The dashboard contains only checked-in public canon metadata. It deliberately has no pretend signed-in user or switchable real role. `services/permissions.ts` is a draft pure policy exercised by tests, not deployed authorization. Even its `authority: server-verified` marker is forgeable in client JavaScript; only a future trusted verifier/rules implementation can make the policy authoritative.

`firebase/firestore.rules.draft` denies all Explorer access by default and is not a deployment configuration. Do not deploy it over existing rules. Before integration, review permission inheritance, ownership, department scope, cross-user isolation, malicious field changes, revoked seals, concurrency, and replay with Firebase emulator tests. No claim of production security readiness is made.

## Existing documentation drift

`Security/Developer-Reference-Protocol.md` describes `scripts/auth.js`, local session tokens, no database, and a single-file mandate. The actual revision uses Firebase and `scripts/auth-guard.js`; the old auth path is absent. Its palette remains useful. The user's explicit modular Next.js directive governs this isolated new subsystem; copying obsolete guards would recreate a broken integration. No existing documentation was edited.
